## 1. The stage rule used (stated before any assignment, per Spec 004 R3.2/R1.2)

- **created** — authored, never run through any check.
- **checked** — lane-1 verification exists: an engine assessment, CI/test evidence, or a
  runnable probe with recorded output.
- **explained** — requires exposition by a **named human**. Ruling: spec/README/changelog
  prose in this corpus is genuine mechanism explanation, but the artifacts name no human
  explainer (authorship is an account, `tbitcs`, and program/agent drafting). Under
  Spec 004's own R3.2 standard — a person, not a tool, model, team alias, or empty
  string — that prose does **not** lift a claim to *explained*. This is the audit's most
  consequential ruling and it is applied uniformly, including to Spec 004 itself.
- **accepted** — requires an identifiable named-human acceptance act whose object is the
  claim or decision itself. Owner merges and directives exist at **document level**
  (Spec 002/003 merged on the owner's order; FR-8 authorized by the owner's OD-1) and are
  recorded as document-level lane-2 state; they do not silently become per-claim
  acceptance. Exactly one claim in the corpus has a claim-level named-human act behind
  it: RT-003-29, the OD-1 decision claim.
- **digested** — explanation + acceptance + incorporation over time. **Nothing in the
  corpus honestly reaches digested, and this audit promotes nothing to it.** A
  retroactive audit cannot manufacture a named human's past digestion.

Where evidence was ambiguous, the lower stage was assigned.

## 4. Nonconformances, grouped by Tao point

Counts are indices into the companion JSON entries, not verdicts; each row names the
mechanism.

**Point 1 — stages (82/82 bundle claims).** No claim in any bundle carries a stage;
`status: supported` was the settlement vocabulary. Worst instance: **Spec 001** — six
claims at 0.999–1.0, header "Baseline (complete — describes shipped behavior)," all on
after_specify test/artifact evidence. That is creation + checking displayed as
settlement, the exact pattern point 1 prohibits. Spec 002/003/004 bundles are internally
honest (outcome claims held at draft/0.481, outcomes ITERATE) — their nonconformance is
the missing stage field, not inflated language; the inflation happened downstream (§5).

**Point 2 — decomposition (partial; structural).** Bundles decompose by FR, and every
formal claim carries its own falsifier (§6). But no headline claim anywhere carries the
five required sub-claims (statement-fidelity / evidence / novelty / attribution /
significance): 0/83 formal claims have a decomposition record. `depends_on` weakest-link
caps exist in the engine but the bundles barely use declared structure — Spec 003's own
FR-8.14 already records the omission limit honestly.

**Point 3 — digestion (83/83 formal claims; all units).** No exposition evidence exists
in any bundle (evidence kinds used corpus-wide: `observed` and `asserted` only). No
claim is tracked as explained by anyone. The `verified_unexplained` risk state Spec 004
R3.3 proposes would, applied retroactively, flag effectively every supported claim in
Specs 001–003.

**Point 4 — attribution (100/100 entries lack an attribution claim).** No bundle
contains an attribution sub-claim; the word "attribution" appears in claims only in
Spec 004 (TA-004-05, TA-004-15) — i.e., only where a claim describes its own absence.
Prose attribution exists and deserves distinguishing from absence:
- Engine 1.1.0–1.4.0: CHANGELOG + `docs/porting-from-epistemic-ledger.md` attribute the
  policy gates / reliability / review queue to the epistemic-ledger program — the
  corpus's best attribution practice, still prose, still unfalsifiable as recorded
  ("measured production rules" is asserted about another program whose measurements are
  not inspectable from this repo).
- Spec 004 attributes its framework to Tao by name with three named sources — prose,
  not a claim; TA-004-15 (its own attribution requirement) is itself draft.
- Red-team findings are attributed to agent teams (RT1–RT4) only; no named humans.
- Spec-kit upstream is credited as host framework in extension materials (prose).
- **Contested attribution: none recorded anywhere** — which under the model reads not
  as "clean" but as "never examined": no attribution claim exists that could be
  contested, so the cap rule has never had anything to bind to.

**Point 5 — anti-gradability (100/100 entries: `not_understood` never stated).** None of
the four assessments carries a residual-unknowns field (verified: key absent in all
four `assessment.json` files). Every assessment's headline is its `summary` tally line
("Assessed N claim(s); found M failure mode(s); K claim(s) below the 0.70 threshold") —
a count presented as the verdict's face. Release and merge surfaces repeat the pattern
(§5 citations). Mitigation, stated fairly: Specs 002/003/004 §-narratives consistently
split problem vs outcome score bands and explain what the numbers mean — legitimate
index-use, and the reason those bundles are "checked, honestly" rather than "checked,
oversold." The overreach is concentrated where tallies travel without their mechanism
text: changelogs, the catalog, and program status language.

**Point 6 — two lanes (4/4 assessments; all reporting).** Every assessment blends one
outcome and one score; no lane-2 quantity exists to report. The clearest retroactive
evidence: Spec 002's implementation was reported in program language as landed while
**T811 — the framework's own lane-1 re-check (after_implement re-assessment) — was never
run** and `assessment.json` still holds the frozen after_specify record, and Spec 003
FR-1 (PR #27) repeated the pattern at smaller scale (tasks.md: 1/79 checked). Lane-1
completion displayed without even lane-1's own closing step, let alone lane 2.

**Point 7 — provenance/priority (partial).** The hash-chain ledger exists, is
tamper-evident for mid-chain edits, and Spec 002 FR-8a made ledgering the default —
real priority infrastructure for *assessments*. But no bundle cites a ledger
registration as priority evidence for a *claim*, git/branch timestamps are the only
claim-level priority record in practice, and RT2 showed the ledger's tail is truncatable
without detection (recorded in Spec 003 FR-4, unimplemented). Openness is not penalized
anywhere found; it is also not yet *protected* at claim level.

**Point 8 — inspectable trails (the corpus's strength, 2 deltas).** Assessments embed
claims, scores with components, failure modes, verdicts, and evidence refs; red-team
findings ship runnable PoCs; Spec 002 FR-3/FR-4 added verify-evidence and version
stamps. Deltas: (a) the trail contains no lane-2 records to inspect (there are none);
(b) the trail for Spec 002's implementation lives in PR bodies and tasks.md, not in an
assessment — the one artifact whose whole purpose is to be the trail.

## 5. Treated-as-settled on checking alone — the concrete cases

1. **Spec 001 baseline** — "complete," six claims `supported` at ~1.0 (see Point 1).
2. **Spec 002 implementation** — "implemented and merged" (repeated in Spec 004's own

   evaluator-side tasks), the frozen assessment is the after_specify one, and spec.md's

   with itself in both directions; both directions are lane conflation.
3. **Spec 003 FR-1** — reported implemented (PR #27) with no bundle re-assessment;
   tasks.md shows 1/79 checked.
4. **Engine 1.2.0/1.3.0 releases** — reliability and the review queue shipped with
   completion language; the red team later showed reliability deserialization
   unvalidated (RT1-05/RT2-C1) and the queue blind to failure-only changes (RT1-18/19).
   The checks that "settled" those releases had not covered the surfaces the language
   implied. (Now recorded in Spec 003 FR-3/FR-8; unimplemented.)
5. **Evaluator contract** — README/schema claims ("provider-neutral," self-attestation
   rule) treated as the contract's behavior while the shipped compose path composes
   empty input to PASS and does not schema-validate in production (RT4 C1/C2). The
   checker did not check the contract.
6. **Extension manifest (pre-fix)** — `extension.yml` declared spec-kit-evaluator a
   required dependency the runner never invoked (RT3-04); corrected on main by PR #17.
   Included because it is the one case already remediated — proof the pattern is
   fixable when checked.

## 9. HISTORICAL LIMITATIONS (unfixable retroactively — labeled, not backfilled)

1. **Digestion of the 1.x releases (1.0.2–1.4.0, Sept–Oct 2026).** No named human
   explained or digested them at the time; that cannot be created after the fact. They
   stand at *checked* permanently unless a future, dated digestion record is written as
   a new artifact (which would be a new lane-2 event, not a retroactive edit).
2. **Catalog submission #4890's public wording.** An upstream issue's filed body;
   its stage-free capability claim and the 1.0.1-vs-1.2.0 lag are history. The fix is
   prospective wording on the next submission.
3. **Evaluator demo verdicts.** Synthetic outcomes shipped without unverified-marking,
   in an artifact that no longer runs; labeling it now would be editing the artifact.
   Recorded here instead.
4. **Release-note tallies** ("Tests: 59 -> 72 passed," "118 tests at baseline") are
   published history on PyPI/GitHub releases; they cannot be un-published. Recorded in
   §5/Point 5; prospective fix is release-note wording discipline.
5. **Authorship identity in past artifacts.** Past bundles/prose name no human authors;
   retroactively inserting names would falsify the record. Git account history
   (`tbitcs`) is the only authorship evidence that exists for those artifacts.
6. **Spec 001's "complete" baseline language** is a merged, frozen record. This audit
   supersedes its *reading* (checked, not settled) without touching the file.

**Fixable prospectively (NOT historical):** running T811 (Spec 002 after_implement
re-assessment) and a Spec 003 post-FR-1 re-assessment; adding `not_understood`
statements to future assessments; any future digestion records — all are new artifacts
or already-specified work (Spec 004 R1–R8, if the owner authorizes implementation).

## 10. Owner decisions this audit surfaces

- **OD-A1 — Ratify the §1 stage rule**, in particular that program/agent-authored prose
  never counts as named-human explanation. If the owner instead counts owner-authored
  prose, several units move to *explained* — but the rule must be chosen, not assumed,
  because every future stage assignment inherits it. (Interlocks with Spec 004 OD-T4.)
- **OD-A2 — T811 and the Spec 003 re-assessment**: run them now (cheap, lane-1, closes
  the worst record divergence) or leave both bundles' implementation claims at checked
  with this audit as the standing caveat?
- **OD-A3 — Spec 001's reading**: accept this audit's reclassification (checked, not
  complete) as the standing interpretation, or commission a fresh baseline spec rather
  than a reinterpretation?
- **OD-A4 — Digestion going forward**: does the owner want dated digestion records
  (named human, per release/spec) as a standing requirement from the next release on —
  i.e., adopt Spec 004 R3 in practice before/independent of implementing it in the
  engine? This audit cannot create them; only the owner's practice can.
- **OD-A5 — Sequencing** (already Spec 004's OD-T1, sharpened by this audit): Spec 003
  FR-2…FR-8 implementation would add another large checked-stage corpus on the old
  vocabulary; the audit's evidence favors deciding OD-T1 before further Spec 003
  implementation lands, so the new work is born stage-tracked rather than audited
  retroactively a second time.
